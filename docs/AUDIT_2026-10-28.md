**Overall:** not assessable as a whole. The audited back end looks careful. The weakest areas are evidence for the published claims and silent degradation.

- **Top commercial blockers:**
  1. The README performance table is not reproducible.
  2. Ownership accuracy is unmeasured while the UI calls it Bayesian.
  3. Stale or fallback data is shown without a label.
- **Top model-integrity risks:**
  1. Hyperparameters were chosen on the same 2025 data used to report the gain (in-sample).
  2. DST actuals omitted return TDs (fixed), so DST training targets and trailing averages were biased.
  3. Name-only identity keys can merge two players' histories (F-07).
- **Top operational and security risks:**
  1. There is no CI test run.
  2. `_optional(...)` and `except Exception` silently drop models.
  3. Raw exception text goes to clients.
- **Verified strengths:**
  - Rolling windows use only `(season, week) < target`.
  - Spread, total and push signs were hand-checked.
  - Optimizer constraints match the DraftKings rules, and Captain is applied once.
  - The Showdown pre-kickoff freeze design is sound.
  - Rate limits and body caps exist, and sign-in is on by default.

## 4. Findings

Severity follows the P0–P3 scale in the brief. "Confirmed" means reproduced or read directly in code; "Hypothesis" means plausible but not demonstrated.

| ID | Pri | Status | Finding and evidence | Recommended fix | Effort / risk |
|---|---|---|---|---|---|
| F-01 | P1 | Confirmed | **Stale data is served as current.** `cache._fetch_and_store` returns a disk entry of any age when a fetch fails and only increments a metric. No endpoint or `SlatePlayers` field carries data age (grep: no `as_of`, `fetched_at` or `stale` in API models). | Return `{source, fetched_at, stale}` for each input and show a banner past a threshold. | M / low |
| F-02 | P1 | Confirmed | **Silent model and input loss.** `slates._optional()` swallows every exception for the role, game and DST models. `projections.build_context` turns a Sleeper failure into `lines = {}`, so everyone falls back to DK FPPG. `defense_vs_expectation` returns `{}` on error. None of this is visible to users. | Record degraded inputs on `SlatePlayers` (a `warnings` list) and show them. Keep the fallbacks. | M / low |
| F-03 | P2 | Confirmed | **README says Classic optimal lineups are Proj and Ceiling.** `app/optimal.py` serves "Safe" and "Tournament" for Classic and marks Ceiling "(retired)". | Update the README. | S / none |
| F-04 | P1 | Confirmed | **Published backtest not reproducible.** README: MAE 5.83 on 2,950 player-games, 4.01 for DSTs, and the matchup adjustment (5.716 to 5.709). | F-05 | P1 | **Fixed** | `matching.find` returned the first of several candidates matching both team and position, silently guessing. | F-06 | P2 | Confirmed | **Solver errors look like "no valid lineup".** `optimizer._solve` returns `None` for infeasible, time-limit and solver error alike. Callers can't tell them apart, and the UI may say "no lineup" when the solver failed. It also re-runs without presolve on any failure. | Return a status. Raise on non-infeasible errors. | S / low |
| F-07 | P2 | Hypothesis | **Name-keyed histories can merge players.** `nflverse_client.player_key` is `name|position` with no team or id. | F-08 | P2 | Confirmed | **Ceiling model out-of-sample window is small and unsegmented.** The stored `test` record (n=1,140; beat rate 0.152) is aggregate only. | F-10 | P1 | Confirmed (design) | **"Bayesian" ownership is a Beta pseudo-count pool.** `ownership_model.py` builds `alpha = Σ mu·N`, `beta = Σ (1-mu)·N` from three model estimates with hand-set effective sample sizes (default N=8 for the prior). ### Performance measurements

Synthetic but realistic pools (seeded; Python 3.13, this sandbox, single run each, so treat as order of magnitude):

| Case | Result |
|---|---|
| Classic optimize, 504 players, 14 games | 141–163 ms |
| Classic "Build for me", 8 lineups (profiled) | 2.5 s, of which **95% is inside HiGHS (`milp`)**; model building in Python is ~30 ms |
| Classic, 20 lineups | 9.3 s (the endpoint caps requests at 5 lineups, so ≈2 s worst case) |
| Showdown optimize, 52 rows | 2 ms |

So the optimizer is not Python-bound and has no cheap win without changing the model (e.g. pre-pruning dominated players, which is not exact once diversity constraints apply, so I did not do it). I **added a 20 s per-solve time limit** (`SOLVER_SECONDS`) so a pathological model raises `SolverError` instead of holding a worker thread.

**Not measured:** page load, slate discovery, player-pool construction, ownership cold start (README: 15–20 s) and warm response, ceiling and breakdown generation, memory, API payload sizes. All need live provider data or a running server with a session token; the p95 < 500 ms and cold-start goals are therefore unverified.
